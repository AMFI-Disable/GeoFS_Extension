# GeoFS Extension Live Verification Report

> [!CAUTION]
> **Educational And Fair-Play Disclaimer**: Use this extension for education and single-player simulation. Respect GeoFS subscriptions, ad-reward entitlements, multiplayer rules, and access controls.

The [five-leg protocol](live-verification-guide.md) remains open. On 18 November 2026 (Singapore time), testing covered the V4 session already open in Chrome, a fresh Chrome for Testing profile with only the extension, and a separate browser control without the extension. The tested extension was v0.2.1 at source revision `4ad877f`. The unpacked path registered in the open Chrome profile pointed at the checkout's `dist`, whose files matched a clean build. The open profile also contained userscript UI. Results from that profile are marked where relevant.

## Findings

| Priority | Finding | Live Evidence And Reproduction |
| --- | --- | --- |
| High | Landing Statistics records false landings after a V4 crash | In the open V4 session, the Phenom 100 showed the native **You crashed** overlay while extension telemetry reported `crashed: false`. The last 100 page diagnostics were all `LANDING_RECORDED`. Several consecutive entries rated near-zero vertical speed as **Butter** and incremented the bounce count from 447 to 450 in under two seconds. Options showed 100 logbook entries, the storage limit, although this run did not inspect the contents of every entry. To reproduce, crash with Landing Statistics running, leave the simulator unpaused, and watch the native crash state, ground contact, and diagnostics. The source reads `aircraft.instance.crashed` in [SimAdapter](../src/core/sim-adapter.ts) and treats each airborne-to-ground transition as a landing in [Landing Statistics](../src/modules/landing-statistics/index.ts). A direct native crash call on a parked Piper Cub in the clean profile set both crash flags to true and did not produce a landing record. The exact trigger for the original crash and the extension-only reproduction of the loop remain open. |
| High | GeoFS V3.9 startup blocks addon verification | A fresh visit to `www.geo-fs.com/geofs.php` reported 3.9 but did not produce an aircraft instance or extension mount. Chrome for Testing captured `Cannot read properties of undefined (reading 'dataProvider')`. The no-extension control reproduced the same exception in GeoFS's `js/geofs.js?kc=3910:367:4900`. This is a simulator startup blocker for this run. |
| Medium | A successful failure recovery emits duplicate diagnostics | On V4, enable Failure Simulator, open CHECKS, and trigger Pitot-Static. The LED turned red and the emergency QRH opened. Clicking REC once restored the LED and the QRH cleared on the next refresh. The same action emitted two consecutive `RESTORE_VERIFIED` events for `pitotStatic`. [Failure Simulator](../src/modules/failure-simulator/index.ts) emits once inside `fix()` and again after successful recovery. |
| Medium | Browser E2E stops at the popup launcher | With Chrome for Testing configured through `CHROME_BIN`, the unpacked extension loaded, but [the runner](../tests/e2e/run-e2e.mjs) timed out on `button:has-text("Side Panel")`. The [popup](../src/popup/app.tsx) now exposes an icon button named `Open Side Panel` through `aria-label`. In a temporary copy, changing the two launcher locators to their accessible names let the runner reach V4. It then timed out waiting for `UI_MOUNT` while still on the default AP++ tab. Live Chrome showed `UI_MOUNT` after switching to **OP / Diag**, so the runner needs to select that tab before asserting diagnostic output. With both test-only adjustments in the temporary copy, the entire mock-simulator E2E suite passed. |
| Low | Initial V4 realism diagnostic reports the wrong capability state | On V4 startup, the first `REALISM_STATE` reported `simMajor: null` and both V3-only features as `ACTIVE`. After telemetry began, the next event correctly reported major 4 and `V4_UNSUPPORTED` for both Vortex Effects and Carrier Ops. The initial event can mislead startup checks. |

## Protocol Coverage

| Leg | Result |
| --- | --- |
| 1. Cold Check | In the extension-only V4 profile at 1280 × 800, the titleless HUD measured 250 px wide at top 70 px, right 20 px, with a 22 px header and all four tabs in one row. In the open V4 profile, the 24 × 40 px left-edge handle appeared on minimize and restored the HUD. Opening and closing A/THR worked, and its expanded LANDING label used `LCD-Bold, monospace`. A/THR, AP++, and OP ENG fit on one row when expanded at both tested widths, 1280 px and 1920 px. The native autopilot settings group and the expanded A/THR group each measured 52 px high in their respective states. `UI_MOUNT` and the final V4 realism states were observed. The Side Panel opened as a regular Chrome tab showed V4 telemetry and `UI_MOUNT` after selecting **OP / Diag**. Native docking and V3.9 remain open. |
| 2. Checklist And Fuel | The V4 CHECKS tab showed all four mandatory procedures and GUIDE. The fuel slider updated the selected value while paused, with the gross weight staying unchanged during the pause. With an unpaused Piper Cub parked at idle, setting fuel to 10% moved the actual aircraft mass from about 467.5 kg to 427.0 kg, and restoring 100% brought it back to 467.5 kg. `FUEL_MASS_SYNC` tracked both changes. Clicking the Piper Cub parking-brake row changed native brake telemetry from off to on. The other hardware actions, timed takeoff comparisons, and tank distribution under load remain open. |
| 3. Climb And Cruise | A/THR and AP++ controls rendered on V4. The high-delta OP-SYNC prompt, thrust handoff, commanded SAS behavior, and cruise gates remain open. |
| 4. Failures And Recovery | V4 Pitot-Static injection, LED, matching emergency QRH, and successful recovery were observed. On the clean Piper Cub, electrical, left main gear, and engine 1 faults also turned their LEDs red and selected their QRHs. Manual FIX returned the LEDs to green and emitted verified restoration for those three faults and Pitot-Static. MCAS, an unsuccessful recovery roll, and physical restoration across multiple aircraft remain open. |
| 5. Approach And Landing | The extension emitted `FPV_BILLBOARD_READY` with the high-resolution variant. The crash-session false landing loop above prevents using that session as a clean touchdown check. Visual FPV in approach, 27 ft retard, spoilers, a clean touchdown and replay, and chocks-on remain open. Options downloaded a Verification Bundle in the clean V4 run. The JSON contained live V4 telemetry, the diagnostics listed above, and zero logbook entries before a test landing. |

Typecheck, all 54 unit tests, and the production build passed. The clean V4 parked layout, fuel, and export run produced no uncaught page errors. A separate V4 fault and crash run logged two uncaught errors with message `aR` and one `mys is not defined`. That run captured messages only. A follow-up run with stack capture timed out waiting for a parked aircraft, so the originating scripts and reproduction steps for those errors remain unverified. The earlier open-profile crash loop was observed through extension diagnostics.
